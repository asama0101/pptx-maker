## 概要
案の選択ページ（`review.html`）に「編集モード」を足す。利用者がブラウザ上で、断片の**文言の書き換え**と、部品の**移動・リサイズ**を直接行い、「Claude に渡す」で貼ると、`choices-import` が差分を機械的に断片（`slides/NN-R*.html`）へ書き戻す。PPTX は、これまでどおり断片 → `final.html` → 測定 → `build` で作る。PowerPoint で直した内容は取り込まない（現状の方針のまま）。

## 経緯と目的（なぜ）
依頼文: 「このスキルで作成した PPTX を人が編集したものを、さらに取り込めるようにしたい」。話し合いの結果、次の理由で、PPTX を編集して戻す案をやめ、HTML 側で直す案にした。

- 直したい内容は、文言と、部品の位置（上下の位置修正・レイアウト変更）。
- PPTX の図形には、断片の要素へ戻る手がかりがない（`build.py` が残す識別子は絵の代替テキストだけ）。文言・順序・座標からの推定になり、文言も位置も直した図形ほど対応づけに失敗する。
- HTML が正本で、PPTX は HTML を測って作る。HTML 側で直せば PPTX に自動で出る。
- 断片の部品（`pp-*`）はすべて `position:absolute` で、位置が `style="left;top;width;height"`（px）で書いてある。ドラッグの結果は、`style` の数値の書き換えで正確に戻せる（推察が要らない）。

利用者の判断: 要素の追加・削除は Claude に依頼する（今回の要件に含めない）。PowerPoint で人が直す必要については扱わない（取り込まない方針は変えない）。

## 目標
1. `review.html` で、選んだ案の文言を書き換えられる。
2. `review.html` で、選んだ案の部品を、ドラッグ・矢印キーで移動し、ハンドルでリサイズできる。画面上では、その場で見た目が変わる。
3. 「Claude に渡す」の JSON に差分（`edits`）が入り、`choices-import` が、検査してから断片に書き戻す。Claude は貼り付けを取り込むだけで、内容を推察しない。
4. 直した断片は、承認・AI 判定を引き継がない（再承認・再判定が要る）。承認の仕組み（指紋）を壊さない。

## 非目標（アンチ目標を含む）
- 部品の追加・削除、案の追加・削除（Claude に依頼する。コメント欄で頼む）。
- PowerPoint で直した PPTX を取り込むこと。
- 表のセル・グラフのデータ（`data-chart`）・絵（`pp-picture`）の中身・画像の差し替えの編集。位置とサイズだけは動かせる。
- 文字の書式（サイズ・色・太字）の編集。
- 段落の追加・削除（構造の変更）。構造が変わる編集は受けない。
- PPTX のリアルタイム更新、ローカルサーバー、常駐プロセス、外部への送信。
- ガイドへの吸着・整列など、図形編集ソフト並みの機能。
- 断片を直したあとの再承認を省くこと。

## 制約
- ページは外へ送らない・Artifact を使わない・CSP のまま。編集のための通信はしない。
- 断片は 1280×720 の座標。画面は縮小表示（`scale = clientWidth/1280`）なので、ドラッグの移動量は scale で割って px に戻す。
- ページ側の変数・ID・クラスは `--rv-`・`rv-` の接頭辞（スライドと同じ DOM・CSS 変数を共有するため）。
- 行末は LF、文書・コメント・コミットは日本語、ruff が通ること。
- 「Claude に渡す」の `check`（`pages` の FNV-1a）は、`edits` を含めた `pages` に対する計算で、JS と Python が一致する。

## 案（検討した進め方）
1. **PPTX を編集して取り込む（Claude が推察して断片を直す）** — 図形から要素への対応づけがなく、位置の直しを CSS に翻訳する推察になる。却下。
2. **PPTX に要素 ID を埋め込み、機械で読み戻す** — 位置は正確だが、ビルド側の変更が大きく、既存の作業フォルダには ID が付かない。HTML が正本という方針と PowerPoint 側の編集が二重になる。却下。
3. **`review.html` に編集モード。貼り付けで書き戻す（採用）** — 新しい常駐プロセスがなく、「外へ送らない」を保てる。保存のたびに貼り付けが要るのが短所。
4. **ローカルサーバーで保存・再測定・ライブプレビュー** — 貼り付けが要らず便利だが、`127.0.0.1` の常駐サーバーを持つことになり、プラグインの性格（読み取り専用・外へ送らない）と CSP の前提を見直す。3 で足りなければ検討する。
5. **今のままコメントで頼む** — 作る物はないが、位置の微調整が遠回りになる。コメントは残し、追加・削除の依頼に使う。

採用の理由: 位置が `style` の px で書いてあり、HTML 側の直しは測定を通して PPTX に自動で出るので、機械で確実に書き戻せる。推察が要らず、実装も小さい。

## 設計（決めたこと）

### 1. 編集の対象と単位
- 対象は、断片の `section.slide` の中の `pp-text`・`pp-shape`・`pp-line`・`pp-image`・`pp-table`・`pp-chart`・`pp-picture`。
- 要素の番号 `i` は、断片の HTML 文字列を文書順にたどり、クラスに上記のどれかを持つ要素に 0 から振る。JS と Python が**同じ規則**で数える。ページ表示では DOM が変わる（グラフのプレビュー、矢印の描画）ので、番号は画面の DOM ではなく、埋め込まれた断片の文字列から数える。
- 文言を直せるのは `pp-text` だけ。直すのは、その要素の中のテキストノードだけで、タグ構造・属性は変えない。
- 位置・サイズは、`style` の `left`・`top`・`width`・`height` を px の整数で上書きする。値が `calc(...)`・`var(...)` などの要素でも、直した項目は px の数値に置き換える（直さなかった項目は書き換えない）。

### 2. 編集してよい部品の絞り込み（私の判断）
- `data-chrome`（題・ヘッドの帯・出典など、固定部分）と `data-ph`（テンプレートのプレースホルダー）の部品は、位置とサイズを動かせない（`chromeSpec`・テンプレートの位置に反するため）。文言だけ直せる。
- `style` に `left`・`top` を持たない部品は、位置を動かせない（`width`・`height` だけ持つなら、その値だけ直せる）。

- 入れ子の部品（ほかの `pp-*` の中にある `pp-*`）は、位置・サイズを動かせない（親の座標系の扱いを避けるため）。文言は直せる。
- 幅・高さは 0 以上の整数（`height:0` の `pp-line` を許す）。負の値は断る。

### 2.1 案と断片の文字列（私の判断）
- 編集は案ごとに持つ。選んでいない案への編集も、`pick` と関係なく、その案の断片へ書き戻す（R1 を編集してから R2 を選んで貼ってもよい）。画面は、編集モードのとき、選んでいる案だけを編集できる。選び直しても、ほかの案の編集は残る。
- `ef` は、`choices.fragment_hash(今の案の断片)` で、承認の `fr` と同じ文字列（`candidates.collect` の整形後）に対して計算する。
- 要素の番号とテキストノードは、`collect` の整形（`svgids.uniquify`・画像の data URI 化）で変わらない（属性だけが変わる）。書き戻す先は、ディスク上の生の断片（`slides/NN-R*.html`）で、番号は生ファイルに対しても同じ規則で数える。この一致を、受入条件 6 のテストで確かめる。

### 3. 画面（編集モード）
- 各ページのカードに「編集」を足す。押すと、大きな表示の選んだ案が編集できる状態になる。編集は案ごとに持つ。
- `pp-text` を押すと、その場で文字を書き換えられる（段落の追加・削除に当たる操作は受けず、元に戻す旨を出す）。部品を選ぶと枠とハンドルが出て、ドラッグで移動、ハンドルでリサイズ、矢印キーで 1px（Shift で 10px）動かせる。
- 「この案の編集を元に戻す」で、そのページのその案の編集を捨てられる。
- 編集はこのブラウザの `localStorage` に自動で残る（キーは既存の選択と同じ指紋つき）。
- 画面上の見た目はその場で変わる。PPTX は変わらない。「PPTX に反映するには、貼り付けのあと、再承認が要る」と画面に添える。
- 編集のあるページは、承認済みでも保存済みに落とす（`touch` と同じ扱い）。

### 4. 貼り付けの形（「Claude に渡す」）
`pages[NN]` に、編集のあるページだけ `edits` を足す。

```
"edits": {"<案>": {"ef": "<断片の指紋>", "items": {"<i>": {"text": ["…", …], "left": 40, "top": 120, "width": 300, "height": 80}}}}
```

- `ef` は、その編集をしたときの、案の断片の指紋（`choices.fragment_hash`）。ページが埋め込む（承認の `fr` と同じ仕組み）。
- `text` は、その要素の空白だけでないテキストノードを文書順に並べた配列（長さが元と同じでなければならない）。
- `left` `top` `width` `height` は、直した項目だけ。整数の px。

### 5. 取り込み（`choices-import` の拡張）
- 新しいサブコマンドは足さない。貼り付けは同じ 1 回で、`edits` があれば、選択の書き込みと同じ取り込みで断片も書く。
- 検査は全件を先に済ませる。次のどれかなら、**全件エラーで何も書かない**: `edits` の形が違う・案がない・`ef` が今の断片の指紋と違う（作り直し前のページから渡された）・要素の番号が範囲外・`text` の長さが違う・`pp-text` でない要素への `text`・動かせない部品への位置の指定・値が整数でない・負の `width`/`height`。
- 書き込みは、断片を `<名前>.new` に書き終えてから置き換える（選択の `_commit` と同じ方針）。書く前に、書き換えた断片を `candidates.unsafe_parts` で確かめ、通らなければ全件エラー。置き換えは選択 → 断片の順で行う。置き換えの途中で失敗すると、一部だけが反映されうる（選択だけが置き換わり断片が元のままだと、そのページは承認が外れ（承認済みだったページは、状態が変わるので `base` も変わり、同じ貼り付けは断られる）。複数の断片の途中で失敗すると、直った断片と直っていない断片が混ざる）。そのときは、`review-page` をやり直して新しいページを開き、直ったかどうかを確かめて、編集をやり直す（編集の下書きは、作り直したページには引き継がれない）。
- 書き換えた案のあるページは、承認済みでも `saved` に戻して書く（`frag` は残さない）。`pick` と `comment` は貼り付けのままにする。AI 判定は、断片の指紋が変わるので自動で `pending` に戻る（既存の仕組み）。
- 戻り値に、書き換えたページと案の一覧を足す。Claude は、利用者に「何ページ・何か所を直したか」を伝え、`review-page` をやり直して再承認してもらう。

### 6. 断片の書き換え
- 元の HTML の文字列を、該当する範囲だけ置き換える（全体を再整形しない）。`style` は、直した項目だけ置換し、順序とほかの宣言は保つ。`left`・`top` のない部品の位置は動かせないので、`style` を新しく作ることはない。
- 文言は HTML のエスケープ（`&`・`<`・`>`）をして書く。

### 7. 文書の更新
`skills/create/SKILL.md`（5 章）、`references/review-flow.md`（ページの説明・取り込み・次の動き）、`README.md`（「作成後の直し」の節）、`CLAUDE.md`（`review-page`・`choices-import` の説明）、`docs/plugin-walkthrough/`（`review.html` の見た目が変わるので、`page.html`・`--shoot`・`SHOT_VERSION`）。

## 受入条件
1. 編集のない貼り付けは、今までと同じに取り込まれる（既存のテストが無修正で通る）。
2. 文言・位置・サイズの編集を含む貼り付けを取り込むと、該当の断片の該当箇所だけが変わる（ほかのバイトは同じ）。pytest が前後の断片の突き合わせで確かめる。
3. 次は全件エラーになり、断片も選択も書かれない: `ef` の不一致・範囲外の番号・`text` の長さ違い・`pp-text` 以外への `text`・動かせない部品への位置の指定・整数でない値・不正な形。
4. 書き換えたページは `saved` になり、承認済みだったページの `frag` が消える。AI 判定は `pending`（断片が変わった）に戻る。`finalize` は、再承認と再判定まで止まる。
5. 取り込んだあとの断片が `collect` を通り、`review-page` → 承認 → `finalize` → `build` で PPTX ができ、移動・リサイズした位置と書き換えた文言が PPTX に出る（E2E の 1 本）。
6. JS と Python の要素番号の数え方が一致する（`collect` 整形後の文字列と生ファイルの両方で）。Playwright で `review.html` を開き、編集を足して「Claude に渡す」の JSON を作り、Python が取り込める（`check` の値も一致する）。グラフ・矢印を含む断片でも一致する。
7. 文言に `<`・`&`・日本語を含む場合の往復が壊れない。
8. ruff が通る。`tests/test_docs.py` が通る。「文書の更新」の項目が更新されている。

## リスク
- JS と Python の要素の数え方がずれると、別の要素を書き換える（`ef` の一致では防げない）。受入条件 6 で防ぐ。
- 画面の縮小・フォント差で、見た目と PPTX の測定結果が少し違う（元からの制約）。直したあとの `review-page` の再測定（R20・R23・R26）と `build` の検査（`overlap`・`overflow`・`keepout`）が最終の判断になる。
- 編集のたびに貼り付け・再承認が要る。何度も微調整する用途には手間になる（案 4 を後で検討する）。
- 文言の編集はテキストノード単位。段落の追加や改行の変更は受けない（Claude に依頼する）。
- `contenteditable` の挙動は環境で異なる（Enter での段落の追加など）。構造が変わる編集は取り消す。

## 組み立てる人に任せること
- 編集 UI の見た目（ハンドルの形、枠の色、ボタンの置き場所）。ただし `--rv-`・`rv-` の接頭辞を守る。
- 要素の番号づけ・テキストノードの取り出しの実装（JS・Python 双方）と、断片の文字列を書き換える方法。
- `localStorage` の編集の保存の形。作り直したページ（断片が変わった）で、古い編集を引き継がない仕組み（`ef` と同じ指紋で判定する）。
- 取り込みの戻り値・エラーメッセージの文言（日本語。既存の書き方に合わせる）。
